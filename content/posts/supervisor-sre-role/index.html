When a Supervisor misbehaves, the old way in is root over SSH with a decrypted password. The SRE Supervisor Role service gives your SSO administrators a read-only kubectl view of the whole Supervisor instead: pods, logs, VKS clusters, VMs and services, but no secrets and no changes. Installed on two Supervisors in my lab in a few minutes.

1 YAMLregistered once per vCenter
~1 minfrom Finish to Configured
0secrets readable, objects changeable

How it works

The service is a small Carvel package. It creates one ClusterRole that can only get, list and watch, and binds it to the SSO group you name at install time. Kubernetes sees SSO groups with an sso: prefix, so Administrators@vcf.lab becomes sso:Administrators@vcf.lab.

Install it

1

Download the service definition

Broadcom supportMy Downloads → vSphere Supervisor Services → SRE Supervisor Role → sre-supervisor-role-v1.0.1.yaml. The same file is in the vsphere-tmm/Supervisor-Services repository.
jump host
$ curl -LO https://raw.githubusercontent.com/vsphere-tmm/Supervisor-Services/main/sre-supervisor-role/sre-supervisor-role-v1.0.1.yaml
2

Register it with vCenter

vCenterSupervisor Management → Services → Add New Service → Upload the YAML → Finish. Do this on every vCenter that has a Supervisor; each workload domain has its own.
3

Install it on the Supervisor

vCenterOn the new card: Actions → Manage Service. Pick version 1.0.1 and the Supervisor, Next, let it validate, Next, and in YAML Service Config set the group. Finish.

Watch for: installing right after registering can fail with signature verification result not found. The Supervisor is still verifying the package. Wait a minute and run Manage Service again.

Use it

Log in as a member of the group, exactly as you would for any Supervisor work. The service namespace now shows up as a context too.

kubectl · log in and check the binding
$ kubectl vsphere login --server 10.1.1.188 --vsphere-username administrator@vcf.lab
Logged in successfully.
You have access to the following contexts:
   10.1.1.188
   svc-sre-supervisor-role-nfqog
   …
$ kubectl get clusterrolebinding supervisor:vmware-system-debug -o wide
NAME                             ROLE                                         GROUPS
supervisor:vmware-system-debug   ClusterRole/supervisor:vmware-system-debug   sso:Administrators@vcf.lab

Takeaways

  • Install it before you need it. It costs one namespace and two RBAC objects, and the next incident starts with kubectl instead of a root password hunt.
  • One group per Supervisor, from that vCenter's SSO domain. Separate workload domains with their own SSO need their own group name.
  • It is a view, not a fix. When something has to change, that is still a job for vCenter, VCF Automation or a support case.
