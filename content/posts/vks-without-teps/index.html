VCF 9.1.1 can run VPC networking without NSX tunnel endpoints. I created a brand-new TEP-less workload domain in my Holodeck lab, put self-service VKS on it through VCF Automation, and ran the same app from the same Git commit on an overlay domain next to it. The network team's whole contribution: one VLAN and a /24.

Starting point: a new workload domain

Nothing existing was converted. Next to the overlay domain wld01, I created a new VI workload domain, tepless-wkld, from scratch: its own vCenter (vc-wld02-a, separate SSO domain), its own NSX Manager (nsx-wld02-a), three fresh ESX hosts (esx-08a–10a) with vSAN, VLAN-backed VPC networking and a Supervisor, all from one run of the workload domain wizard. The overlay domain kept running untouched beside it, which is what makes the side-by-side comparison later in this post possible.

Why it matters

Overlay VPCs need tunnel endpoints on every host: a TEP VLAN, an MTU of at least 1700 on the physical network, and routing for the overlay. That is often where a VCF project waits on the network team. A VLAN-backed VPC removes all three, and you still get a VPC with a transit gateway, load balancers, the distributed firewall and self-service through VCF Automation.

  • Simpler physical network. No TEP VLAN, no jumbo frames, no overlay routing: a normal VLAN with a gateway.
  • Nodes are first-class citizens on that VLAN. VKS nodes get routable addresses, answer directly, and leave the cluster with their own IP, so firewalls and logs see which node talked.
  • Nothing changes for application teams. Same VKS, same VCF Automation self-service, same Argo CD and Git workflow.

What I built

The lab runs two workload domains side by side behind one router. wld01 is a classic overlay domain with TEPs (region east-1), wld02 is the TEP-less one (region tepless). VCF Automation serves both, and one Argo CD instance in the overlay region deploys to clusters in both.

Inside the TEP-less domain, two networks keep responsibilities apart: SDDC Manager creates the Day-0 VLAN for the Supervisor itself, and VCF Automation gets its own Day-1 VLAN for the organizations' workloads. The router only needs a gateway on each.

Build it, step by step (GUI)

1

One wizard: workload domain, TEP-less networking and Supervisor

In VCF 9.1.1 the TEP-less part is not a separate project. It is one page of the normal workload domain wizard, and the same wizard can deploy the Supervisor too.

Workload Domains+ Workload Domain → VI – Workload Domain. Eleven steps: general information, vCenter, cluster, image, NSX Manager, storage, hosts, distributed switch, vSphere Supervisor, review, validation.

The result is visible on every host: the VMkernel adapters stop at management, vMotion, vSAN and the Supervisor.

The whole feature in one comparison: the overlay host carries vmk10 and vmk11 on the nsx-overlay stack (the TEPs). The TEP-less host has none.

2

Kubernetes releases for the Supervisor

The Supervisor came with the domain. It still needs a source of VKS releases, and it is worth giving your administrators a read-only kubectl view of the Supervisor before anything goes wrong.

vCenterContent Libraries → Create → Subscribed, https://wp-content.broadcom.com/v2/latest/lib.json, download when needed. Then Supervisor → Configure → General → Kubernetes Service → Add the library.
3

A second VLAN for VCF Automation

SDDC Manager gave the entire VLAN 202 range to its Day-0 block. VCF Automation creates its own IP block in NSX and cannot overlap it, so give the region a Day-1 VLAN: a gateway on the router for VLAN 203, 10.203.203.1/24, on the same trunk.

4

VCF Automation: region, IP block, connection, organization

Provider portalInfrastructure → vCenter → Refresh the new workload vCenter first. Then Regions → New: the domain's NSX Manager, its Supervisor, the storage class.
Provider portalNetworking → External IP Blocks → New: 10.203.203.0/24 in the region. External Connections → Distributed VLAN Connections → New: VLAN 203, gateway 10.203.203.1/24, that IP block.
Provider portalOrganizations → New (All-Apps): region quota, VM classes, storage class, share the VLAN 203 connection with an IP quota, and the first organization administrator.
5

The organization's namespace and a public subnet

Org portalBuild & Deploy → create a namespace in region tepless (class small). Then Services → (namespace) → Network → SubnetSets → New SubnetSet: access mode Public, 32 addresses.

The namespace's VPC details tell the TEP-less story on their own: no private IP block, no default SNAT IP, a load balancer address on the VLAN.

6

Create the VKS cluster

Org portalServices → Kubernetes → Create → Custom Configuration. Release v1.36.2 (or the one offered), OS image Ubuntu, control plane 1 × best-effort-small, node pool 2 × best-effort-medium. Under Network, tick "Use custom primary network" and pick SubnetSet public.

That last setting is the one TEP-less rule. With Default Configuration the request is refused, because VKS falls back to a private network that a VLAN-backed VPC does not have.

7

The same cluster from Git

The wizard writes a Cluster API object. Keeping it in Git makes the build repeatable; the TEP-less part is one variable:

  variables:
  - name: networks
    value:
      interfaces:
        primary:
          network:
            apiVersion: crd.nsx.vmware.com/v1alpha1
            kind: SubnetSet
            name: public

Applied with kubectl apply -f straight from the repository, demo-git came up with two running nodes, including the one-time download of the v1.36.2 Ubuntu image. Argo CD, running on the overlay region's Supervisor as described in GitOps on VCF 9.1 with the Argo CD Supervisor Service, then deploys the same test app to both networks from one Git path.

To be fair to the overlay: I built a third cluster, overlay-public, from the same Git file on the overlay domain, with its nodes on a public VPC subnet. From outside it behaves like TEP-less: nodes answer directly and leave with their own address. So routable nodes are not unique to TEP-less. What is unique is that you get them without TEPs, jumbo frames or overlay routing, and that public is the only mode, so nobody has to remember to choose it.

Two rows are the same on purpose. The NSX load balancer proxies in both models, and the pod MTU of 1450 comes from the Kubernetes CNI (Antrea) inside the cluster. The MTU benefit of TEP-less is real, but it lives on the hosts and the physical network, which is where step 1's screenshots show it.

What to watch for

Every item below happened in this build. None is hard to fix once you know the message.

VCF Automation cannot create its IP block

IP Space Block tepless is not found

The Day-0 block already owns the VLAN's /24. Give VCF Automation its own VLAN and range.

The region refuses the Supervisor

zones … do not have a network stack configured

VCF Automation has not seen the new domain yet. Refresh the vCenter in the provider portal, then retry.

No Kubernetes versions to pick

namespace is missing … Kubernetes releases

Attach the subscribed library under Supervisor → Configure → General → Kubernetes Service.

Default Configuration is refused

cannot be deployed with default network(private) in a VPC namespace without SNAT

Use Custom Configuration with a Public SubnetSet as the primary network (VKS 3.7).

No matching node image

Missing compatible KR/OSImage … / Multiple OSImages resolved

Right after subscribing, newer releases may only offer Ubuntu images while the catalog syncs (about an hour). In YAML, pin both os-name and os-version.

Downloads fail on an older library

SSL Certificate mismatch … certificate_unknown

A library subscribed weeks ago may still trust Broadcom's old certificate. Edit the library and accept the current certificate. It hit the overlay side of this lab, not the TEP-less one.

Namespaces from the API need more

Zone should be specified … / Storage Class should be specified

If the namespace class does not set them, give the zone (with CPU and memory limits and reservations) and a storage class with a limit.

Argo CD on another Supervisor

automatic registration only covers its own Supervisor

Register the TEP-less cluster with a standard Argo CD cluster secret, and allow TCP 6443 to the Day-1 range in Argo CD's firewall policy.

Lab tip: check names against the lab's own DNS. The jump host's resolver had a stale record for the TEP-less NSX Manager, which nearly sent this build in the wrong direction.

The concept in one picture

Both models give you VPCs, a transit gateway, load balancers and the distributed firewall. The difference is what a packet looks like on the physical network, and therefore what that network has to support.

Verdict

TEP-less is the easiest way I have found to get VPCs and self-service Kubernetes onto a network you do not control: one VLAN, one /24, no MTU change. The trade-off is that every workload address is public on that VLAN, by design. Plan the Day-1 range and the firewall rules around that, and VKS, VCF Automation and Argo CD work as they do on an overlay.
