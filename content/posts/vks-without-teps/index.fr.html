VCF 9.1.1 peut faire tourner le réseau VPC sans tunnel endpoints NSX. J'ai créé un tout nouveau workload domain TEP-less dans mon labo Holodeck, j'y ai mis du VKS en libre-service via VCF Automation, et j'ai fait tourner la même app, issue du même commit Git, sur un domaine overlay voisin. Toute la contribution de l'équipe réseau : un VLAN et un /24.

Point de départ : un nouveau workload domain

Rien d'existant n'a été converti. À côté du domaine overlay wld01, j'ai créé de zéro un nouveau VI workload domain, tepless-wkld : son propre vCenter (vc-wld02-a, domaine SSO distinct), son propre NSX Manager (nsx-wld02-a), trois hôtes ESX neufs (esx-08a–10a) avec vSAN, le réseau VPC VLAN-backed et un Supervisor, le tout en une seule exécution de l'assistant de workload domain. Le domaine overlay a continué de tourner à côté sans être touché, ce qui rend possible la comparaison côte à côte plus loin dans ce billet.

0interface tunnel endpoint (TEP) sur les hôtes ESX
1 VLAN + /24ce que le réseau physique fournit par région, en MTU 1500

Pourquoi c'est important

Les VPC overlay exigent des tunnel endpoints sur chaque hôte : un VLAN TEP, un MTU d'au moins 1700 sur le réseau physique et du routage pour l'overlay. C'est souvent là qu'un projet VCF attend après l'équipe réseau. Un VPC VLAN-backed supprime ces trois exigences, et on obtient quand même un VPC avec transit gateway, load balancers, pare-feu distribué et libre-service via VCF Automation.

  • Un réseau physique plus simple. Pas de VLAN TEP, pas de trames jumbo, pas de routage overlay : un VLAN normal avec une passerelle.
  • Les nœuds sont des citoyens à part entière sur ce VLAN. Les nœuds VKS reçoivent des adresses routables, répondent directement et sortent du cluster avec leur propre IP ; les pare-feu et les journaux voient donc quel nœud a communiqué.
  • Rien ne change pour les équipes applicatives. Même VKS, même libre-service VCF Automation, même flux de travail Argo CD et Git.

Ce que j'ai construit

Le labo fait tourner deux workload domains côte à côte derrière un seul routeur. wld01 est un domaine overlay classique avec TEP (région east-1), wld02 est le domaine TEP-less (région tepless). VCF Automation dessert les deux, et une seule instance Argo CD dans la région overlay déploie vers des clusters des deux côtés.

Dans le domaine TEP-less, deux réseaux séparent les responsabilités : SDDC Manager crée le VLAN Day-0 pour le Supervisor lui-même, et VCF Automation reçoit son propre VLAN Day-1 pour les workloads des organisations. Le routeur n'a besoin que d'une passerelle sur chacun.

La construction, étape par étape (GUI)

1

Un seul assistant : workload domain, réseau TEP-less et Supervisor

Dans VCF 9.1.1, la partie TEP-less n'est pas un projet à part. C'est une page de l'assistant normal de workload domain, et ce même assistant peut aussi déployer le Supervisor.

Workload Domains+ Workload Domain → VI – Workload Domain. Onze étapes : informations générales, vCenter, cluster, image, NSX Manager, stockage, hôtes, switch distribué, vSphere Supervisor, revue, validation.

Le résultat est visible sur chaque hôte : les adaptateurs VMkernel s'arrêtent à la gestion, vMotion, vSAN et au Supervisor.

Toute la fonctionnalité en une comparaison : l'hôte overlay porte vmk10 et vmk11 sur la pile nsx-overlay (les TEP). L'hôte TEP-less n'en a aucun.

2

Des versions Kubernetes pour le Supervisor

Le Supervisor est venu avec le domaine. Il lui faut encore une source de versions VKS, et il vaut la peine de donner à vos administrateurs une vue kubectl en lecture seule du Supervisor avant que quoi que ce soit tourne mal.

vCenterContent Libraries → Create → Subscribed, https://wp-content.broadcom.com/v2/latest/lib.json, téléchargement when needed (au besoin). Ensuite Supervisor → Configure → General → Kubernetes Service → ajouter la bibliothèque.
3

Un deuxième VLAN pour VCF Automation

SDDC Manager a donné toute la plage du VLAN 202 à son bloc Day-0. VCF Automation crée son propre bloc IP dans NSX et ne peut pas le chevaucher ; donnez donc à la région un VLAN Day-1 : une passerelle sur le routeur pour le VLAN 203, 10.203.203.1/24, sur le même trunk.

4

VCF Automation : région, bloc IP, connexion, organisation

Provider portalInfrastructure → vCenter → d'abord Refresh sur le nouveau vCenter du workload domain. Ensuite Regions → New : le NSX Manager du domaine, son Supervisor, la storage class.
Provider portalNetworking → External IP Blocks → New : 10.203.203.0/24 dans la région. External Connections → Distributed VLAN Connections → New : VLAN 203, passerelle 10.203.203.1/24, ce bloc IP.
Provider portalOrganizations → New (All-Apps) : quota de région, VM classes, storage class, partager la connexion VLAN 203 avec un quota d'IP, et le premier administrateur de l'organisation.
5

Le namespace de l'organisation et un sous-réseau public

Org portalBuild & Deploy → créer un namespace dans la région tepless (classe small). Ensuite Services → (namespace) → Network → SubnetSets → New SubnetSet : access mode Public, 32 adresses.

Les détails du VPC du namespace racontent à eux seuls l'histoire TEP-less : aucun bloc IP privé, aucune IP SNAT par défaut, une adresse de load balancer sur le VLAN.

6

Créer le cluster VKS

Org portalServices → Kubernetes → Create → Custom Configuration. Release v1.36.2 (ou celle proposée), image OS Ubuntu, control plane 1 × best-effort-small, node pool 2 × best-effort-medium. Sous Network, cocher « Use custom primary network » et choisir le SubnetSet public.

Ce dernier réglage est la seule règle propre au TEP-less. Avec Default Configuration, la demande est refusée, car VKS se rabat sur un réseau privé qu'un VPC VLAN-backed n'a pas.

7

Le même cluster depuis Git

L'assistant écrit un objet Cluster API. Le garder dans Git rend la construction reproductible ; la partie TEP-less tient en une variable :

  variables:
  - name: networks
    value:
      interfaces:
        primary:
          network:
            apiVersion: crd.nsx.vmware.com/v1alpha1
            kind: SubnetSet
            name: public

Appliqué avec kubectl apply -f directement depuis le dépôt, demo-git a démarré avec deux nœuds en marche, téléchargement unique de l'image Ubuntu v1.36.2 compris. Argo CD, qui tourne sur le Supervisor de la région overlay comme décrit dans GitOps sur VCF 9.1 avec le Supervisor Service Argo CD, déploie ensuite la même app de test sur les deux réseaux depuis un seul chemin Git.

Pour être juste envers l'overlay : j'ai construit un troisième cluster, overlay-public, à partir du même fichier Git sur le domaine overlay, avec ses nœuds sur un sous-réseau VPC public. Vu de l'extérieur, il se comporte comme le TEP-less : les nœuds répondent directement et sortent avec leur propre adresse. Les nœuds routables ne sont donc pas propres au TEP-less. Ce qui l'est, c'est de les obtenir sans TEP, sans trames jumbo ni routage overlay, et que le mode public soit le seul possible : personne n'a à se souvenir de le choisir.

Deux lignes sont identiques, et c'est voulu. Le load balancer NSX fait proxy dans les deux modèles, et le MTU de 1450 des pods vient du CNI Kubernetes (Antrea) à l'intérieur du cluster. Le gain de MTU du TEP-less est réel, mais il se situe sur les hôtes et le réseau physique, là où les captures d'écran de l'étape 1 le montrent.

Points de vigilance

Chaque point ci-dessous s'est produit pendant cette construction. Aucun n'est difficile à corriger une fois qu'on connaît le message.

VCF Automation ne peut pas créer son bloc IP

IP Space Block tepless is not found

Le bloc Day-0 possède déjà le /24 du VLAN. Donnez à VCF Automation son propre VLAN et sa propre plage.

La région refuse le Supervisor

zones … do not have a network stack configured

VCF Automation n'a pas encore vu le nouveau domaine. Faites un Refresh du vCenter dans le provider portal, puis réessayez.

Aucune version Kubernetes à choisir

namespace is missing … Kubernetes releases

Rattachez la bibliothèque abonnée sous Supervisor → Configure → General → Kubernetes Service.

Default Configuration est refusée

cannot be deployed with default network(private) in a VPC namespace without SNAT

Utilisez Custom Configuration avec un SubnetSet Public comme réseau principal (VKS 3.7).

Aucune image de nœud compatible

Missing compatible KR/OSImage … / Multiple OSImages resolved

Juste après l'abonnement, les versions récentes peuvent n'offrir que des images Ubuntu le temps que le catalogue se synchronise (environ une heure). En YAML, fixez à la fois os-name et os-version.

Les téléchargements échouent sur une bibliothèque plus ancienne

SSL Certificate mismatch … certificate_unknown

Une bibliothèque abonnée il y a quelques semaines peut encore faire confiance à l'ancien certificat de Broadcom. Modifiez la bibliothèque et acceptez le certificat actuel. Le problème a touché le côté overlay de ce labo, pas le côté TEP-less.

Les namespaces créés par l'API en demandent plus

Zone should be specified … / Storage Class should be specified

Si la classe de namespace ne les définit pas, indiquez la zone (avec limites et réservations de CPU et de mémoire) et une storage class avec une limite.

Argo CD sur un autre Supervisor

automatic registration only covers its own Supervisor

Enregistrez le cluster TEP-less avec un cluster secret Argo CD standard, et autorisez TCP 6443 vers la plage Day-1 dans la politique de pare-feu d'Argo CD.

Astuce de labo : vérifiez les noms auprès du DNS du labo lui-même. Le résolveur de l'hôte de rebond avait un enregistrement périmé pour le NSX Manager TEP-less, ce qui a failli envoyer cette construction dans la mauvaise direction.

Le concept en une image

Les deux modèles offrent des VPC, une transit gateway, des load balancers et le pare-feu distribué. La différence, c'est l'allure d'un paquet sur le réseau physique, et donc ce que ce réseau doit prendre en charge.

Verdict

Le TEP-less est le moyen le plus simple que j'aie trouvé pour amener des VPC et du Kubernetes en libre-service sur un réseau que vous ne contrôlez pas : un VLAN, un /24, aucun changement de MTU. La contrepartie : chaque adresse de workload est publique sur ce VLAN, par conception. Planifiez la plage Day-1 et les règles de pare-feu en conséquence, et VKS, VCF Automation et Argo CD fonctionnent comme sur un overlay.
