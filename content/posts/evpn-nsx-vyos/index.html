1 · EVPN route types in one screen

EVPN is a single MP-BGP address family (L2VPN / EVPN) that carries several distinct route (NLRI) types. You rarely touch them by hand — the control plane emits whichever it needs — but knowing which is which is what lets you read show bgp l2vpn evpn output and reason about a broken path.

TypeNameWhat it carriesRole in this design
1Ethernet Auto-DiscoveryPer-ES / per-EVI reachability for a multihomed segmentFast convergence & aliasing across multihomed PEs. Not used — single-homed lab.
2MAC / IP AdvertisementHost MAC, optionally MAC + IP, per L2VNIThe L2 workhorse — bridging & ARP/ND suppression. Present, but not our focus.
3Inclusive Multicast (IMET)Per-VNI flood list for BUM (ingress replication)Builds the flood tree for any L2VNI you extend.
4Ethernet SegmentES discovery + Designated-Forwarder electionMultihoming only. Not used here.
5IP PrefixIP prefixes decoupled from MAC — the IP-VRF / L3VNI routeThe whole point of this build. NSX and VyOS trade tenant subnets as Type-5.

Types 6–10 (SMET, IGMP/MLD join-sync, S-PMSI) exist for optimized multicast and aren't in play. In a pure Type-5 design like this, the border advertises prefixes and the receiver installs them into an IP-VRF — no MAC state crosses the boundary.

Why your workload VM shows as a /32

Here's the practical consequence that trips people up. NSX's distributed VXLAN connection doesn't advertise the workload subnet — it advertises a host route per live VM. So a VM on the NSX public subnet 10.55.55.0/28 lands in the FRR VRF RIB as a /32, with the ESX host TEP as the next-hop (reachable over the L3VNI), not a subnet route via a gateway:

evpn-prj-2# show ip route vrf evpn-prj-2 10.55.55.3
B>* 10.55.55.3/32 [20/0] via 10.1.3.135, br65020 onlink, 21:57:20

The B>* is the EVPN Type-5 route, selected and installed; 10.1.3.135 is the ESX host TEP; [20/0] is the eBGP admin distance (200 if you kept §5 as iBGP). The /28 itself never crosses — only the /32s of VMs that are actually up. §8 traces the full L3 path this route drives.

2 · Why EVPN to mesh the IP fabrics

The lab has an NSX overlay on one side and a VyOS-fronted physical fabric on the other. Both are separate routing domains; the job is to make tenant subnets on one reachable from the other, cleanly and per-tenant. EVPN is the tool because:

  • One BGP control plane for L2 and L3. The same MP-BGP session carries MAC reachability (Type-2), the BUM flood list (Type-3) and IP-prefix reachability (Type-5). No flood-and-learn, no second protocol to stitch the fabrics.
  • Multi-tenancy is native. Each tenant is a VRF with its own Route Distinguisher and Route Targets. Overlapping tenant IP space never collides on the wire, and isolation is the default — you leak between tenants only when you deliberately choose to.
  • Overlay is decoupled from the underlay. Any routed IP underlay works; VXLAN encapsulates VTEP-to-VTEP in the data plane. Add a tenant by adding a VNI, not by re-architecting the transport. The opposite trade-off, no overlay and no TEPs at all, is what VKS on a VLAN-backed VPC looks like.
  • Type-5 keeps MAC state off the border. The PE/TOR routes on IP — prefixes, or here per-host /32s — and never needs the MAC tables of everything behind the overlay, which is ideal for hanging an NSX domain off a physical EVPN fabric.
  • Distributed, direct forwarding. In NSX's DGTW model, routing is distributed across the ESXi hosts. The route controller advertises workload /32s with the host TEP as next-hop, so tenant traffic egresses host-to-fabric without hairpinning through a central SR.
  • Vendor-neutral. NSX, FRR/VyOS, Cisco, Arista and Nokia all speak the same EVPN AFI/SAFI. This build literally proves NSX ↔ VyOS interop end to end.

3 · RD and RT, drawn

These two values do all the multi-tenant work, and they are the thing most people get backwards. They are not the same knob:

RD · 65000:70001
Route Distinguisher — uniqueness

Prepended so the prefix is globally unique in BGP. The same 10.70.1.0/24 from a different VRF or router carries a different RD, so overlapping tenant IPs never clash. It does not decide where a route lands.

RT · 65000:70001
Route Target — membership

The import/export filter. A receiver installs the route only into a VRF whose import RT matches the route's export RT. Identical both ends here → prj-1 ↔ prj-1; different from prj-2 → no leak. This is your tenant boundary.

L3VNI · 70001
The data-plane segment

Once the control plane picks a path, the L3VNI is the VXLAN segment the packet is encapsulated into. Control plane chooses; VNI carries.

The one asymmetry that bites everyone: RTs must be identical on both ends, but RDs must be different between NSX and the fabric (NSX documents this requirement explicitly). You type NSX's RD explicitly on the connection (it is a field — e.g. prj-2's 65020:20), so it is not auto-derived; keeping it different from the VyOS VRF's RD is on you. Setting the same value on both sides is exactly what broke prj-2 until VyOS was moved to 65000:65020. Keep RT symmetric (route-target both) and let the two sides carry distinct RDs.

5 · The VyOS config

VyOS (FRR under the hood) is the border. Two moving parts: the overlay BGP sessions to the route controller in the default VRF (one per VTEP) carrying EVPN for every VNI, and, per tenant, a tenant VRF with an L3VNI bridge plus a per-VRF BGP block that re-originates the VRF's routes as Type-5. Everything below is set-mode, apply with configure; …; commit; save.

5.1 · Underlay + the EVPN overlay sessions

# ── routed underlay to the two route-controller VTEPs (one per tenant) ──
set interfaces ethernet eth1 address '10.66.66.1/24'   # prj-1 VTEP
set interfaces ethernet eth2 address '10.77.77.1/24'   # prj-2 VTEP

# ── global BGP: eBGP to the route controller (AS 65010), one neighbor per VTEP ──
set protocols bgp system-as '65000'

set protocols bgp neighbor 10.66.66.2 remote-as '65010'
set protocols bgp neighbor 10.66.66.2 update-source '10.66.66.1'
set protocols bgp neighbor 10.66.66.2 address-family l2vpn-evpn

set protocols bgp neighbor 10.77.77.2 remote-as '65010'
set protocols bgp neighbor 10.77.77.2 update-source '10.77.77.1'
set protocols bgp neighbor 10.77.77.2 address-family l2vpn-evpn

set protocols bgp address-family l2vpn-evpn advertise-all-vni

AS & peering (confirmed from EVPN-RC): the route controller runs local AS 65010, so this is eBGP — the VyOS neighbor's remote-as is 65010 (the RC's AS), and the RC in turn sees VyOS as remote-as 65000. The deployed lab peers per tenant VTEP: VyOS 10.66.66.1 ↔ RC 10.66.66.2 (prj-1) and VyOS 10.77.77.1 ↔ RC 10.77.77.2 (prj-2), both max-hop 1 — see the controller snapshots in §6.1. Both VTEP neighbors are configured above, and each tenant's VXLAN sources from its own VTEP (see §5.2–§5.3).

5.2 · Tenant VRF — evpn-prj-1

# ── the VRF and its symbolic L3VNI ──
set vrf name evpn-prj-1 table '10001'
set vrf name evpn-prj-1 vni '70001'

# ── L3VNI transport: VXLAN iface bound into a bridge, bridge into the VRF ──
set interfaces vxlan vxlan70001 vni '70001'
set interfaces vxlan vxlan70001 source-address '10.66.66.1'
set interfaces vxlan vxlan70001 parameters nolearning
set interfaces bridge br70001 member interface vxlan70001
set interfaces bridge br70001 vrf 'evpn-prj-1'

# ── a local prefix so the VRF has something to originate as Type-5 ──
set interfaces dummy dum70001 address '10.70.1.1/24'
set interfaces dummy dum70001 vrf 'evpn-prj-1'

# ── per-VRF BGP: re-originate the VRF's IPv4 routes as EVPN Type-5 ──
set vrf name evpn-prj-1 protocols bgp system-as '65000'
set vrf name evpn-prj-1 protocols bgp address-family ipv4-unicast redistribute connected
set vrf name evpn-prj-1 protocols bgp address-family l2vpn-evpn advertise ipv4 unicast
set vrf name evpn-prj-1 protocols bgp address-family l2vpn-evpn rd '65000:70001'
set vrf name evpn-prj-1 protocols bgp address-family l2vpn-evpn route-target both '65000:70001'

5.3 · Second tenant is the same pattern — evpn-prj-2

Adding tenant B is just the VRF block again with its own VNI, RD and RT. It rides the overlay sessions from 5.1 — advertise-all-vni already covers every VNI, so there is no per-VNI BGP config to add; prj-2 simply sources its VXLAN from its own VTEP (10.77.77.1), which is why 5.1 carries the second neighbor.

set vrf name evpn-prj-2 table '10002'
set vrf name evpn-prj-2 vni '65020'

6 · The NSX side — and the traps

NSX 9.1 can run EVPN on the distributed transit gateway, not only a Tier-0. The object chain, from the workload up to the peer, is: a workload VM on a VPC subnet → the VPC and its connectivity profile → a transit gateway → an attachment to a distributed VXLAN connection (which holds the L3VNI/RD/RT) → the route controller on a VNA cluster, which is the box that actually peers BGP with VyOS. Below is what each object is for, with the live configuration from the lab.

6.1 · Route controller (the BGP speaker)

The route controller (EVPN-RC) runs on the VNA cluster in Active-Standby HA and owns the EVPN sessions to VyOS. It carries two interfaces and two BGP neighbors — one per tenant VTEP — with local AS 65010, so the sessions to VyOS (AS 65000) are eBGP. Multipath Relax is on — it lets paths with different AS-paths qualify as equal for multipath — though ECMP itself is off here. Both neighbors report Success — the control plane is up.

6.2 · Distributed VXLAN connection (L3VNI + RD + RT)

This is the EVPN identity of the tenant on the NSX side. The connection type is Distributed VXLAN with Services: EVPN — NSX describes it as integrating with a fabric via BGP EVPN for route advertisement and direct host-to-fabric VXLAN. Each tenant's connection carries its EVPN L3 VNI, an explicitly-typed Route Distinguisher, and import/export Route Targets, all bound to the EVPN-RC route controller. Connectivity Type is L3 Only (Route Type 5) — prefixes, no L2. These must line up with the VyOS VRF: VNI equal, RT equal, RD distinct.

6.3 · Assign the external connection to the project

A distributed VXLAN connection isn't consumable by a tenant until it's assigned to that tenant's project. In Manage Projects, editing evpn-prj-1 and setting its External Connectivity associates the connection from §6.2 (for prj-1, Distributed-vxlan-wld01) — shown here as External Connections: 1. The Set External Connections dialog picks it in two places — External Connections (available to the project's VPCs) and External Connections for Default Transit Gateway (the connection the project's built-in transit gateway uses) — both set to Distributed-vxlan-wld01. Only once it's assigned can the project's VPCs and transit gateways attach to it. The project also anchors the tenant's External IP Blocks (the ranges its VPC subnets draw from — 2 here) and its Edge / Virtual Network Appliance cluster (the one VNA cluster where the route controller runs).

Why this is its own step: the project is the isolation boundary — a connection is available only to the projects it's assigned to, here evpn-prj-1 alone. This is where the tenant separation you enforced with RD/RT in the fabric becomes an administrative boundary in NSX too: prj-2's VPCs can't attach prj-1's connection, and vice-versa.

6.4 · Transit gateway + attachment

The transit gateway is per project; attaching it to the external connection is what binds the connection into the datapath. Editing evpn-prj-1-dgtw, the Connection type is Distributed VXLAN and the External Connection is Distributed-vxlan-wld01 — the one assigned to the project in §6.3. NSX states the dependency inline: the TGW connectivity type is selectable only once external connections are assigned. The VPC Transit Subnets (100.64.0.0/21 by default) are the internal transit range the VPC uses to reach the transit gateway — plumbing, not something you advertise.

6.5 · VPC, connectivity profile, and the Public subnet

The workload lives on a VPC subnet, and the subnet's Access Mode is the single most important setting in the whole build — it decides whether the subnet is advertised at all, and it's immutable after creation, so get it right up front. Both tenants' workload subnets are Access Mode: Public with VPC Gateway Connectivity on, each drawing from its own IP block: prj-1's public is 10.21.21.64/26 from dgtw-block in evpn-prj-1-vpc-1; prj-2's pub is 10.55.55.0/28 from ext-prj-2 in prj-2-vpc-1 — two projects, two public subnets, the same route controller keeping them apart by RD/RT.

6.6 · Workload attached, and the route on the wire

With VMs live on the Public subnets, the route controller originates each workload's /32 as EVPN Type-5, and both ends line up. On the RC (its tier0_sr), get bgp neighbor 10.66.66.1 advertised-routes shows the two host routes it sends: prj-1 10.21.21.67/32 (RD 65001:70001, next-hop host TEP 10.1.3.133) and prj-2 10.55.55.3/32 (RD 65020:20, next-hop 10.1.3.135) — and the identical pair goes to the other VTEP neighbor 10.77.77.1.

Why both tenants show up on one session

The route controller is a single BGP speaker holding every EVPN route, so when it advertises to a neighbor it sends its entire EVPN table — both RDs, both tenants — down each session. That is expected, not a leak: the RD makes each prefix globally unique, and tenant separation is enforced at import, not at advertisement. The receiver installs a route only into the VRF whose import RT matches the route's RT, so seeing prj-1's and prj-2's prefixes on the same wire is normal — they diverge the instant they're imported.

VyOS confirms the other half. show bgp l2vpn evpn neighbors 10.66.66.2 routes lists both prefixes under their distinct RDs: 65001:70001 carrying RT:65000:70001 (→ imported into evpn-prj-1) and 65020:20 carrying RT:65020:20 (→ evpn-prj-2). The AS-path is 65010 (eBGP from the RC), the encapsulation ET:8 is VXLAN, and each route carries the advertising host's router-MAC (Rmac). Because the RC sends the same routes out both its VTEPs, VyOS learns each /32 twice — best (*>) on one session, multipath-eligible (*=) on the other — giving it two equal-cost paths to the host.

Proof of life: the /32 the RC advertises (§1, §8) is exactly what VyOS receives here, tagged with the RT that files it into the right tenant VRF. That's the control plane closed end to end — the matching data-plane path is §8.

6.7 · Why only the matching route lands in each VRF

§6.6 showed both tenants' /32s crossing every session — so why doesn't prj-2's route appear in prj-1's routing table? Because import RT is a filter. A received EVPN route sits in the global L2VPN-EVPN table, but FRR installs it into a tenant VRF's RIB only if the route's RT matches that VRF's route-target both. The result is clean per-tenant tables:

Reading the evpn-prj-1 table: B>* 10.21.21.67/32 [20/0] via 10.1.3.133, br70001 onlink is the imported Type-5 route — its RT 65000:70001 matched the VRF, so it's in. prj-2's 10.55.55.3/32 (RT 65020:20) is absent: it was received on the session, but its RT didn't match, so it never entered this VRF. The recursive next-hop resolves out br70001 — the L3VNI bridge for VNI 70001 — which is what encapsulates the packet toward the host TEP (the data-plane path in §8).

Two more things the table shows:

  • The (dup) second path is the same prefix learned from the RC's other VTEP (§6.6) — both resolve to the same next-hop, so FRR keeps one and flags the duplicate. That's the two-VTEP redundancy landing in the RIB.
  • The connected routes — C>* 10.70.1.0/24 and L>* 10.70.1.1/32 on dum70001 — are the local prefixes VyOS originates back to NSX as Type-5 (the reverse direction). Each VRF advertises its own connected subnet and imports the far side's host routes; that symmetry is the whole point of meshing the two fabrics.

Tenant isolation, mechanically: the fabric floods everything, the RD keeps it unique, and the import RT decides membership. Same RT both ends → the route lands; different RT → it's filtered out. No ACL, no VRF leak — just RT matching. To deliberately share between tenants, you add a cross-VRF import (see the note after §8).

6.8 · The traps, collected

1 · A distributed VXLAN connection advertises host /32s, not the subnet. The route controller sends per-workload /32 routes with the host TEP as next-hop — it does not advertise the subnet prefix. If you're waiting to see 10.55.55.0/28 cross to VyOS, you'll wait forever; you'll see 10.55.55.3/32 once a VM is up.

2 · Only Public subnets originate. The attachment's default rule is PUBLIC, and NSX refuses to change it to TGW_PRIVATE on an EVPN attachment (it returns a 612520 "not supported" error). A VM on a Private – Transit Gateway subnet (Private_TGW in the API) has nothing eligible to advertise — this is the classic "NSX peers fine but announces nothing" symptom.

3 · RD distinct, RT identical. Covered above — and it's an NSX-side trap because you type both RDs by hand (NSX's on the connection, VyOS's on the VRF), so nothing stops you setting them equal. Keep them different — NSX prj-2 65020:20 vs VyOS 65000:65020.

4 · No N-S service gateway on an EVPN-attached TGW. Enabling the VPC service gateway (centralized SNAT) is rejected by design when the transit gateway has a distributed VXLAN connection attachment. EVPN routing and the stateful N-S gateway are mutually exclusive here.

7 · The Holodeck underlay — the holorouter

Here's the failure mode that eats an afternoon: the EVPN control plane comes straight up — session Established, prefixes exchanged — but pings fail, because the data plane can't form. In a nested Holodeck, everything routes through the holorouter (a Photon L3 hub at 10.0.6.33) that masquerades every interface. Left alone, it SNATs the VXLAN outer IPs, so the ESX host TEPs (10.1.3.0/24) and VyOS's VTEP subnets never actually reach each other. Two things fix it: a route so the holorouter can reach the VTEP subnets via VyOS's management leg, and NAT exemptions so the TEP↔VTEP flows keep their real addresses.

Per-tenant VTEPs: each project has its own VTEP subnet — prj-1 10.66.66.0/24, prj-2 10.77.77.0/24 — which is why there are two routes and two pairs of exemptions above, and why §5 configures a VTEP source per tenant. Collapse both onto a single VTEP source and you would need only one route and one pair of exemptions; the pattern is identical, only the address count changes.

7.1 · Routes — reach the VTEP subnets via VyOS's mgmt leg

# on the holorouter (root@10.0.6.33) — path to each VTEP subnet via VyOS eth0
ip route add 10.66.66.0/24 via 10.1.1.250     # prj-1 VTEP subnet
ip route add 10.77.77.0/24 via 10.1.1.250     # prj-2 VTEP subnet

These resolve out eth1.10 (VLAN 10, where 10.1.1.250 lives). Before them, both VTEPs were UNREACH from the holorouter; after, both ping REACH. This route is the decisive change.

7.2 · NAT exemptions — don't masquerade TEP↔VTEP

# inserted at the TOP of nat POSTROUTING, above KUBE-POSTROUTING and the MASQUERADE catch-alls
iptables -t nat -I POSTROUTING -s 10.66.66.0/24 -d 10.1.3.0/24 -j ACCEPT
iptables -t nat -I POSTROUTING -s 10.1.3.0/24 -d 10.66.66.0/24 -j ACCEPT
iptables -t nat -I POSTROUTING -s 10.77.77.0/24 -d 10.1.3.0/24 -j ACCEPT
iptables -t nat -I POSTROUTING -s 10.1.3.0/24 -d 10.77.77.0/24 -j ACCEPT

Two things to know: these are runtime-only — a reboot wipes every rule and route in this section (see 7.4 to persist). And unlike the earlier classic-edge rules, these carry no --comment tag, so at cleanup you identify them by subnet — or re-add each with -m comment --comment evpn-dgtw to make them greppable.

7.3 · Verify & roll back

# verify — 4 ACCEPTs at the top, route resolves, both VTEPs reachable
iptables -t nat -L POSTROUTING -n --line-numbers | head

7.4 · Make it survive a reboot (Photon)

Drop the two ip route add and four iptables -I lines into a script and wrap it in a oneshot unit. Make the iptables inserts idempotent (check-then-add) so re-runs don't stack duplicates.

# /etc/systemd/system/evpn-holo.service   →   systemctl enable --now evpn-holo
[Unit]
After=network-online.target
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/evpn-holo.sh
[Install]
WantedBy=multi-user.target

8 · The full L3 path — following the /32

Putting §1's /32 together with the underlay from §7: here is what actually happens, hop by hop, when something in the fabric sends a packet to the workload 10.55.55.3 on the NSX public subnet 10.55.55.0/28. The routing decision is made on the /32; VXLAN is only the transport between the two L3 contexts.

HopL3 deviceAction — destination 10.55.55.3
1VyOS · VRF evpn-prj-2RIB lookup hits 10.55.55.3/32 (the /32, not the /28); next-hop is host TEP 10.1.3.135, egress over L3VNI 65020.
2VyOS VTEP 10.77.77.1VXLAN encapsulation — inner dst 10.55.55.3; outer 10.77.77.1 → 10.1.3.135.
3ESX host TEP 10.1.3.135Underlay delivers the frame (routed via the holorouter, §7); the host decapsulates VXLAN and maps VNI 65020 → tenant IP-VRF.
4NSX distributed routerAnycast gateway for the VPC routes to the connected public subnet 10.55.55.0/28.
5VM tiny-vm-t2Frame delivered to 10.55.55.3 on the public subnet.

The return path is symmetric: the NSX distributed router holds VyOS's Type-5 prefixes (e.g. 10.65.20.0/24) in the tenant IP-VRF and encapsulates back toward the VyOS VTEP. Because forwarding is distributed, each host TEP talks to the VyOS VTEP directly — there is no central service router hairpinning the traffic.

Inter-tenant note

By design, prj-1 and prj-2 can't reach each other — separate VRFs and RTs is the point. If you want controlled cross-tenant reachability, leak on VyOS with a per-direction import vrf (optionally scoped by a route-map), and be aware the NSX-side attachment's strict uRPF may need relaxing for the hairpinned path. That's a deliberate hole in isolation, so do it selectively.

# leak prj-2's routes into prj-1 and vice-versa (VyOS-local; use a route-map to scope)
set vrf name evpn-prj-1 protocols bgp address-family ipv4-unicast import vrf evpn-prj-2
set vrf name evpn-prj-2 protocols bgp address-family ipv4-unicast import vrf evpn-prj-1
